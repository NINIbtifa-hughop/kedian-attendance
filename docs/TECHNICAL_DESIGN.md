# 电子点名册 MVP 技术方案

## 1. 文档目的

本文给出电子点名册 MVP 的技术实现方案，作为开发、测试和后续演进的共同依据。方案以产品设计文档为准，优先实现单教师、单设备、无需登录、离线可用的版本。

本阶段的核心原则是：

- 先验证点名和课时统计的真实价值，不提前建设账号、云同步和复杂权限。
- 数据默认留在当前设备，同时提供清晰、可靠的备份与恢复手段。
- 把业务规则放在独立领域层中，避免页面代码直接承担课表生成和统计逻辑。
- 保留未来增加云同步的空间，但不为尚未验证的需求增加 MVP 复杂度。

## 2. 技术选型

| 领域 | 选择 | 用途与理由 |
| --- | --- | --- |
| 应用框架 | React + TypeScript | 生态成熟，适合构建组件化、响应式的单页应用；TypeScript 用于约束核心数据模型 |
| 构建工具 | Vite | 开发启动和构建速度快，PWA 集成简单 |
| 路由 | React Router | 管理班级、点名、历史和统计等页面 |
| 样式 | Tailwind CSS | 快速建立移动端优先的响应式界面和统一设计令牌 |
| 无障碍组件 | Radix UI（按需使用） | 用于对话框、下拉菜单等需要键盘操作和焦点管理的组件 |
| 本地数据库 | IndexedDB + Dexie.js | 支持结构化数据、事务、索引和版本迁移，适合关系较多的离线业务数据 |
| 数据校验 | Zod | 校验表单、CSV、备份文件和数据库迁移边界的数据 |
| 日期处理 | date-fns | 处理月份、星期、日期格式和课表生成，避免手写日期算法 |
| CSV | Papa Parse | 解析和生成名单、课程明细及统计 CSV |
| 轻量界面状态 | Zustand（确有需要时引入） | 只保存筛选条件、未提交交互状态等；持久业务数据不放入全局状态仓库 |
| 离线安装 | vite-plugin-pwa | 生成 Web App Manifest 和 Service Worker，缓存应用外壳 |
| 单元/组件测试 | Vitest + React Testing Library | 验证领域规则、表单和关键组件行为 |
| 端到端测试 | Playwright | 在真实浏览器中验证导入、点名、重开应用和导出流程 |

首版采用纯静态部署，可选择 Cloudflare Pages、Netlify 或 GitHub Pages。运行时不需要应用服务器或数据库服务器。

## 3. 总体架构

应用采用离线优先的分层结构：

```text
React 页面与组件
        │
用例层（点名、生成课程、统计、导入导出）
        │
领域层（实体、状态机、课时与统计规则）
        │
仓储接口与数据映射
        │
Dexie / IndexedDB
```

各层职责如下：

- **界面层**：呈现数据、收集用户操作、显示校验和确认信息，不自行计算月度课时。
- **用例层**：组织一次完整操作，例如生成某月课程、提交一节课点名、导入学生或恢复备份。
- **领域层**：包含课程状态、出勤状态、课表生成、课程状态确认和月度统计等纯业务规则。领域函数尽量保持无浏览器依赖，以便快速测试。
- **数据层**：负责 IndexedDB 表、事务、查询、迁移，以及领域对象与持久化记录之间的转换。

建议目录结构：

```text
src/
  app/                 # 路由、应用入口、全局错误边界
  features/
    classes/           # 班级与学生
    schedules/         # 固定课表与月度课程生成
    attendance/        # 点名与课程确认
    history/           # 历史记录
    reports/           # 月度统计和 CSV
    backup/            # 完整备份与恢复
  domain/              # 无 UI 依赖的实体、类型和规则
  db/                  # Dexie schema、仓储和迁移
  shared/              # 通用组件、日期、校验与错误处理
tests/
  e2e/
```

## 4. 核心数据模型

所有主键使用由应用生成的 UUID。时间点使用 ISO 8601 字符串；用于课表计算的本地日期单独保存为 `YYYY-MM-DD`，避免时区换算使课程跨日。MVP 的业务时区使用设备当前时区。

### 4.1 班级 `Class`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | UUID | 内部唯一标识 |
| `name` | string | 班级名称 |
| `note` | string? | 备注 |
| `archivedAt` | datetime? | 归档时间；归档后默认不出现在点名入口 |
| `createdAt` / `updatedAt` | datetime | 审计时间 |

### 4.2 学生 `Student`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | UUID | 即使姓名相同也保持独立 |
| `classId` | UUID | 所属班级 |
| `name` | string | 姓名 |
| `note` | string? | 备注 |
| `archivedAt` | datetime? | 移除名单时归档，不物理删除历史 |
| `createdAt` / `updatedAt` | datetime | 审计时间 |

同一班级允许重名。界面发现重名时应展示备注或简短内部区分信息，但不得通过姓名关联历史记录。

### 4.3 固定课表 `RecurringSchedule`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | UUID | 唯一标识 |
| `classId` | UUID | 所属班级 |
| `weekday` | 1—7 | ISO 星期一至星期日 |
| `startTime` | `HH:mm` | 本地开始时间 |
| `effectiveFrom` | date | 生效日期 |
| `effectiveTo` | date? | 可选结束日期 |
| `createdAt` / `updatedAt` | datetime | 审计时间 |

### 4.4 课程实例 `Lesson`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | UUID | 唯一标识 |
| `classId` | UUID | 所属班级 |
| `scheduleId` | UUID? | 来源固定课表；临时新增时为空 |
| `localDate` | date | 上课日期 |
| `startTime` | `HH:mm` | 上课时间 |
| `source` | `scheduled` | `manual` | 计划生成或临时新增 |
| `status` | `pending` | `held` | `all_absent` | `cancelled` | 待确认、已上课、全员未到/未开课、其他取消 |
| `cancellationReason` | string? | 其他取消时必填 |
| `note` | string? | 本节备注 |
| `createdAt` / `updatedAt` | datetime | 审计时间 |

固定课表只负责生成计划，课程实例才是统计和点名依据。固定课表改变后不得自动改写已生成或已点名的课程。对于同一 `scheduleId + localDate + startTime` 建立唯一性约束或执行幂等检查，防止重复生成。

临时调课按显式操作处理：保留原课程实例并标为“其他取消”（注明调课），再创建新的手工课程实例。这样计划数、取消数和实际上课数都有可追溯含义。若产品之后希望调课只算一次计划课，需要先确定新的统计口径，再调整模型。

### 4.5 出勤记录 `AttendanceRecord`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | UUID | 唯一标识 |
| `lessonId` | UUID | 课程实例 |
| `studentId` | UUID | 学生内部标识 |
| `studentNameSnapshot` | string | 点名当时的姓名快照 |
| `status` | `present` | `late` | `leave` | `absent` | 出勤、迟到、请假、缺勤 |
| `updatedAt` | datetime | 最后修改时间 |

同一 `lessonId + studentId` 只能有一条记录。保存姓名快照可保证学生改名或归档后，历史记录仍可理解。每次提交一节课的点名及课程状态时使用一个 IndexedDB 事务，避免只保存了一部分学生。

### 4.6 应用元数据 `AppMetadata`

保存数据库 schema 版本、首次使用时间、上次完整备份时间等信息。它不替代 Dexie 的数据库迁移版本，只用于应用功能提示和备份兼容判断。

## 5. 关键业务规则

### 5.1 月度课程生成

1. 读取目标班级在目标月份内生效的固定课表。
2. 按设备本地日历计算匹配星期的日期。
3. 为每个日期构造待确认课程。
4. 以课表、日期和时间执行幂等写入，重复点击不会生成重复课程。
5. 已存在的课程实例不随固定课表后续修改而改变。

可以在打开某班级的目标月份时自动补生成，也应提供显式的“生成/检查计划”入口和生成结果提示。自动生成必须仍然是幂等的。

### 5.2 点名和课程确认

- 进入点名页时，默认加载该节课发生时属于班级且未归档的学生；若课程已有记录，则以已有记录为准。
- “全部出勤”只更改当前编辑草稿，用户保存后才写入数据库。
- `held` 表示课程实际进行，并计入教师课时。迟到视为实际到课。
- 当所有记录都是缺勤时，系统不能自动决定课时，必须要求教师明确选择 `held` 或 `all_absent`。
- `cancelled` 必须填写取消原因，且不保存虚假的全班出勤记录。
- 已完成课程允许再次编辑；MVP 只保留最新结果和 `updatedAt`，暂不建设完整版本审计。

界面上应把“学生出勤状态”和“课程是否实际进行”表现为两个相关但不同的问题，避免将全员缺勤直接等同于取消。

### 5.3 月度统计口径

统计范围由 `classId` 和课程 `localDate` 所在月份决定：

- 计划课程数：范围内全部未归档课程实例数，包括临时新增课程。
- 实际上课数：`status = held`。
- 全员未到/未开课数：`status = all_absent`。
- 其他取消数：`status = cancelled`。
- 待确认数：`status = pending`。
- 出勤汇总：只汇总有出勤明细的课程，并分别累计四种学生状态。比例的分母是纳入汇总的出勤记录总数，页面和导出文件须说明这一口径。

为了避免首版中出现存储结果和重新计算结果不一致，月度统计在查询时由课程与出勤记录计算，不单独持久化汇总表。数据量增长后再评估缓存。

## 6. IndexedDB 设计与迁移

建议索引：

```text
classes:            id, name, archivedAt
students:           id, classId, [classId+archivedAt]
recurringSchedules: id, classId, [classId+effectiveFrom]
lessons:            id, classId, localDate, [classId+localDate],
                    &[scheduleId+localDate+startTime]
attendanceRecords:  id, lessonId, studentId, &[lessonId+studentId]
appMetadata:        key
```

实现时需要验证 Dexie 对可空复合索引的行为。若 `scheduleId` 为空不能稳定参与唯一索引，则新增非空 `generationKey`：固定课表课程使用确定性键，手工课程使用 UUID；由用例层保障生成幂等。

每次 schema 变化都通过 Dexie 版本升级声明完成，迁移函数需要有自动化测试。禁止在应用启动时静默清空无法解析的数据；迁移失败时应停止写入，提示用户先导出可恢复的数据或使用上一版本。

## 7. 导入、导出、备份与恢复

### 7.1 CSV

- 学生名单导入至少支持 `name`、`note` 两列，允许中文表头映射。
- 导入前完成编码、空姓名、超长字段和重复行校验，并显示预览与错误行。
- 同名学生是合法数据；同一文件中的完全重复行应提示用户选择是否保留，而不是擅自合并。
- 月度导出包含课程日期、时间、课程状态、取消原因、学生状态和统计口径。
- CSV 输出使用 UTF-8 BOM，提升中文内容被常见表格软件直接打开时的兼容性。

### 7.2 完整 JSON 备份

CSV 用于阅读和结算，不能可靠表达全部关联关系，因此另提供完整 JSON 备份：

```json
{
  "format": "attendance-register-backup",
  "version": 1,
  "exportedAt": "2026-10-15T10:00:00+08:00",
  "data": {
    "classes": [],
    "students": [],
    "recurringSchedules": [],
    "lessons": [],
    "attendanceRecords": []
  }
}
```

恢复前必须使用 Zod 校验文件格式、版本、主外键和枚举值。MVP 采用“验证通过后整体替换”的恢复策略：先在内存中完成全部验证，再在单个事务中替换数据；开始前二次确认，并建议用户先导出当前备份。任何校验或写入失败都不得留下半恢复状态。

应用首页应提示本地数据的边界，并在较长时间没有备份时进行非阻塞提醒。不能宣称 Service Worker 或 IndexedDB 等同于云备份。

## 8. PWA 与离线策略

- Service Worker 只缓存应用外壳和静态资源；业务数据始终由 IndexedDB 管理。
- 首次打开需要网络下载应用，完成后可离线使用核心功能。
- 新版本采用“发现更新—提示用户—用户确认后刷新”的策略，避免在点名编辑中强制刷新。
- 部署必须使用 HTTPS，并设置正确的 SPA 路由回退。
- 不缓存或上传学生照片；MVP 不申请相册、相机、定位和通知权限。

浏览器“清除网站数据”、隐私模式、设备故障仍可能造成数据丢失，这是本地优先 MVP 的已知限制，须在首次使用和备份入口中明确说明。

## 9. 页面与交互实现重点

### 9.1 点名页

- 移动端优先，学生姓名与四种状态操作在无需横向滚动的区域内完成。
- 页面顶部固定显示课程信息、未保存状态和各状态实时人数。
- “全部出勤”必须明显但避免与“保存”相邻造成误触；保存成功后提供明确反馈。
- 离开有未保存更改的页面时给出提示。
- 所有状态不能只依靠颜色区分，需要文字或图标；交互目标满足触屏尺寸要求。

### 9.2 删除和归档

- 班级和学生默认采用归档，保留历史关联。
- 尚未产生历史数据的错误记录可以物理删除，但仍需二次确认。
- 删除课程将影响月度统计，首版优先提供“其他取消”而非物理删除；确需删除临时误建课程时明确展示影响。

### 9.3 错误处理

- 可恢复错误在操作附近显示，例如 CSV 某行字段错误。
- 数据库不可用、存储空间不足或迁移失败使用全局错误页，并禁止继续产生用户误以为已保存的数据。
- 不在日志中输出完整学生名单或备份内容。纯前端 MVP 默认不接入远程行为分析。

## 10. 安全与隐私

MVP 不包含账号和服务器，但仍处理学生姓名，因此需要遵循数据最小化：

- 只保存姓名和可选备注，不采集照片、联系方式、定位或生物信息。
- 不使用第三方 CDN 动态加载运行时代码、字体或脚本，构建产物自包含。
- 对 CSV 单元格中以 `=`, `+`, `-`, `@` 开头的用户内容进行转义，降低电子表格公式注入风险。
- 备份文件不加密，因此导出时提示用户妥善保管；不在共享设备下载目录长期留存。
- CSP 至少限制脚本和资源来源为自身，并避免使用不必要的 `unsafe-eval`。
- 所有导入内容都视为不可信文本，通过 React 默认转义显示，不用 `dangerouslySetInnerHTML`。

## 11. 测试与质量保障

### 11.1 单元测试

优先覆盖：

- 不同月份长度、跨年和闰年下的固定课表生成。
- 生效区间、重复生成和固定课表修改后的历史隔离。
- 全员缺勤时的显式课程确认。
- 四种课程状态及出勤状态的月度统计。
- 同名学生依靠 UUID 区分，学生改名后历史快照不变。
- CSV 解析、公式注入转义、JSON 备份版本和关联完整性校验。
- 每一次数据库 schema 迁移。

### 11.2 组件测试

覆盖全部出勤、单独修改、未保存离开提醒、取消原因必填、删除确认、导入错误预览和键盘操作。

### 11.3 端到端测试

至少建立以下浏览器流程：

1. 创建班级并导入含重名学生的 CSV。
2. 创建固定课表并生成目标月份课程。
3. 完成一节正常点名并修正误操作。
4. 处理全员缺勤并明确选择课程状态。
5. 验证月度统计并导出 CSV。
6. 关闭并重新打开页面，确认 IndexedDB 数据仍存在。
7. 导出完整备份、清空测试数据、恢复备份并核对关联记录。
8. 在离线模式下重新打开已安装应用并完成点名。

CI 建议执行类型检查、Lint、单元/组件测试、生产构建和 Playwright Chromium 测试。发布前补充手机尺寸和桌面尺寸的人工冒烟检查。

## 12. 实施阶段

### 阶段一：工程骨架与数据层

建立 React/Vite/TypeScript、路由、设计令牌、Dexie schema、仓储接口、迁移测试和 PWA 基础配置。

### 阶段二：班级、学生与课表

完成班级和学生维护、CSV 名单导入导出、固定课表、月度课程幂等生成及相关测试。

### 阶段三：点名与历史

实现点名核心页面、事务保存、课程状态确认、历史课程和学生月度明细。优先在真实手机浏览器上验证操作效率。

### 阶段四：统计、备份与发布

完成月度统计、CSV 报表、完整 JSON 备份恢复、离线端到端测试、隐私提示和静态部署。

每个阶段都应交付可运行的纵向切片，不把测试和数据迁移推迟到最后。

## 13. 暂缓事项与演进方向

MVP 明确不建设云端同步、账号、多角色、通知、照片和教务系统集成。出现以下信号后再评估服务端：

- 同一教师必须在多台设备之间使用同一份数据。
- 多名教师需要协作维护班级。
- 机构需要集中备份、权限、审计或结算。

届时可选择 PostgreSQL + Supabase（认证、数据库和对象级权限），前端继续保留 IndexedDB 作为离线缓存。但这不是简单地把本地表上传：必须另外设计用户/机构归属、数据权限、删除语义、版本号和同步冲突策略。

若浏览器平台在目标设备上出现无法接受的存储或安装限制，可在保持领域层和 React 界面的前提下评估 Tauri 封装桌面应用。当前阶段不建议使用 Electron 或同时开发原生移动端。

## 14. 待产品确认的问题

以下问题不阻塞工程骨架，但应在实现对应功能前确认：

1. 临时调课是否计为“一次取消 + 一次新增计划”，还是统计上仍只算一节计划课。本文暂按前者设计。
2. `迟到` 是否在所有统计中都算实际到课；本文暂按实际到课处理。
3. 学期中途加入或退出的学生，生成旧课程时是否应该出现在未点名名单中。本文建议以课程当时已有的记录为准，新课程使用当前有效名单。
4. CSV 月度导出需要“每节课一行”“每位学生每节课一行”，还是同时提供两种。本文建议统计摘要和出勤明细分别导出。
5. 是否需要为班级设置时区。MVP 暂使用设备当前时区，若教师跨时区使用则需升级模型。

这些决定应形成产品规则并补充自动化测试，避免仅靠页面实现中的隐含假设。
